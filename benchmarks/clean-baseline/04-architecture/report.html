Failure and ownership boundaries

CurrentQueue exhaustion

Retries use exponential backoff for up to six attempts. After that, the event enters a dead-letter queue. The source does not specify recovery ownership or replay behavior from that queue.

ProposedEvidence hold

Missing, unreachable, or changed source is a review hold, not a verified state. Preserve the partner-supplied URL as received; any correction needs an explicit, auditable operator action.

SecuritySecret isolation

The dashboard reads normalized event and review status, not the raw webhook secret. The reviewer asks how secrets are kept out of logs; no logging control is specified in the supplied design.

UnresolvedReplay and duplicate posting

There is no confirmed replay UI or idempotency guarantee for the proposed resolver. It is unknown whether replay can produce duplicate dashboard updates.

Audit requirementOne event ID through final status

Maintain a trace from receipt through normalization, resolution, policy outcome, any human review, and final dashboard status using the event ID. Exact storage, retention, and correlation mechanisms remain design decisions.

04

Questions to close before implementation

How are secrets kept out of logs?

Set a logging and redaction contract at receipt and downstream boundaries. The supplied facts state the dashboard read boundary, but do not confirm log controls.

How can an operator correct a false hold?

Define an authorized review action that records the operator, reason, source URL treatment, and outcome against the same event ID. The mechanism is open.

Can replay duplicate dashboard updates?

Unknown. Confirm resolver and dashboard write idempotency behavior, then define replay semantics and duplicate detection before offering replay.

Where does auditable state live?

Database and deployment topology are not selected. Choose them after defining event-ID traceability, status history, and ownership across the pipeline.
