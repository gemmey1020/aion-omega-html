Keep source evidence attached to every event decision

The proposal inserts source resolution and a policy gate between normalization and dashboard publication. Its key boundary is clear: evidence gaps stop automated posting and route the event to a human review state; they never become a “verified” label.

Design status: The resolver and policy service are proposed components. The database and deployment topology are not selected. Replay UI and resolver idempotency are unconfirmed.

Failure and ownership boundaries

Proposed ownership lanes to resolve in design.

Source and provenance

Resolver records reachability, content hash, retrieval time, and status. It must retain the partner’s source URL unchanged. Missing, unreachable, and changed sources trigger hold.

Proposed owner: resolver service

Eligibility and review

Policy service owns the automated-post eligibility decision. A human reviewer must be able to assess held events; the correction mechanism and authority are not yet specified.

Proposed owners: policy service + review operator

Queue exhaustion

Current retries use exponential backoff for up to six attempts. After that, the event enters a dead-letter queue. Recovery and replay ownership are not confirmed.

Current mechanism: intake queue / dead-letter queue

Dashboard publication

Dashboard reads normalized event and review status, not the raw webhook secret. Duplicate updates after replay remain a risk because idempotency is not guaranteed.

Boundary: publisher to dashboard

Secret handling

Secret exclusion from dashboard reads is specified. Secret redaction from logs and other observability output is not described and needs an explicit control and owner.

Open control: ingestion / logging path

Audit continuity

Maintain event ID from receipt through final status, including resolver result, policy decision, human review, retries, and dead-letter disposition.

Decisions still needed

Questions raised by the security reviewer and engineering team.
How are secrets kept out of logs?

Specify redaction at intake, resolver, policy, queue diagnostics, and dashboard publishing as applicable; assign an accountable owner. The present case confirms only that dashboard reads exclude the raw secret.

How can an operator correct a false hold?

Define review access, evidence shown, correction authority, reason capture, and the event ID audit record for the decision.

Can replay duplicate dashboard updates?

Yes, this remains an open risk: no idempotency guarantee is confirmed for the proposed resolver, and replay UI is unconfirmed. Define deduplication behavior and replay semantics before relying on replay.

What stores state and where does it run?

Database and deployment topology have not been selected. Select them with the event ID audit requirement and operational ownership in view.
